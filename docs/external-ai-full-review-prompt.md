# 履约异常处理台外部 AI 独立前后端逻辑审查提示词

你现在是一名独立的资深全栈代码审查员，不是实现者。

请完整阅读当前压缩包中的代码，以及 `docs/front-back-logic-review.md`。对这个“销售履约异常处理台”进行一次前后端逻辑正确性审查。

目标不是总结项目、评价视觉效果或只检查语法，而是尽可能发现现有单元测试、评估脚本和一次浏览器演示没有发现的逻辑问题、状态错乱、数据覆盖、错误降级、证据链断裂、租户隔离问题、并发问题和前后端契约问题。

## 审查边界

1. 以当前代码为准。不要盲信 README、注释、计划书、审查说明或已有测试；文档中的问题只能作为线索，必须重新检查代码。
2. 不要修改任何源代码、测试、文档或配置，不要删除文件，不要更新 Git 标签，不要生成修复提交。
3. 可以运行本地测试和本地服务，但只允许访问 `127.0.0.1` 或 `localhost`。不要访问公网服务、远程服务器或第三方 API。
4. 不要要求任何 Secret、Cookie、Access Token、SSH 配置、真实服务器地址、真实客户资料或用户数据。
5. 如果无法验证，必须明确写成“无法验证”，不能用猜测补全结论。
6. 每个问题都必须给出具体文件路径、行号、触发条件和证据。不要只写“可能有风险”。
7. 先读代码，再决定是否运行测试。不要因为测试通过就默认逻辑正确。

## 代码范围和系统主链

请重点阅读以下文件和调用关系：

- `src/workbench/index.html`：单页前端、状态变量、DOM 渲染、事件绑定、CTA 和 API 调用。
- `src/server.ts`：HTTP 路由、请求头租户/操作者、初始化案件、错误处理和 API 响应。
- `src/case/runtime.ts`：状态机、逐项差异核对、提案、审批、执行、核验和结案。
- `src/store.ts`：按租户 JSON 文件加载、保存、读改写和并发边界。
- `src/types.ts`：案件、证据、冲突、动作、审计事件和状态类型。
- `src/evidence/extract.ts`、`src/conflict/detect.ts`、`src/report/build.ts`：材料抽取、字段归一、差异检测、报告和引用。
- `src/agents/graph.ts`、`src/eval/run.ts`、`src/gold-set/cases.ts`、`src/gold-set/it-ops.ts`：流程编排、评估和合成数据。
- `tests/pack.test.ts`、`tests/workbench-ui.test.ts`、`contracts/openapi.yaml`、`contracts/evidence-pack.v1.json`：测试与契约。

当前核心流程是：

```text
new → triaged → confirmed → proposed → approved → executed → verified → closed
```

前端通过 `overview / investigate / resolve` 三个层级表达流程。用户在 `investigate` 中逐项标记冲突为已核对，后端通过 `POST /api/cases/:id/review` 保存 `reviewedConflictIds`；材料缺口或未完成差异核对时，不应进入 `proposed`。

## 一、前端逻辑审查

- 首次加载、切换案件、切换能力模块、返回一览、重新渲染时，`currentId`、`currentLevel`、`currentModule`、`caseRows`、`caseGate`、报告、回执和已核对差异是否串线。
- 成功加载、接口失败、空案件、案件不存在、报告失败和能力模块失败时，旧 DOM、旧状态、旧按钮和旧提示是否残留。
- 快速连续切换案件或连续点击差异核对按钮时，旧请求是否会覆盖新请求，页面是否会显示过期状态。
- `reviewingConflict` 的前端门禁是否真的阻止并发点击，重绘后按钮是否恢复正确，失败后是否允许重试。
- `overview / investigate / resolve` 页签、阶段锁定、CTA、返回按钮和能力模块入口是否使用同一套放行条件。
- `new`、`triaged`、`confirmed`、`proposed`、`approved`、`executed`、`verified`、`closed`、`rejected` 在页面文案、按钮和颜色上是否一致。
- 差异数量、已核对数量、材料缺口、报告状态、关系图、进度条和队列状态是否来自同一个实时案件对象。
- 来源卡中的左右证据、字段值、定位、原文、风险等级和“已核对”状态是否可能错位。
- `innerHTML`、`escapeHtml`、Markdown、引用原文、文件名、URL、案件标题和 API 返回值是否存在 XSS、属性注入或 HTML 结构破坏。
- 动态 DOM 重绘后事件监听、焦点、键盘操作、禁用状态、`aria` 属性和移动端横向滚动是否仍正确。
- 旧案件完成后切换到新案件，处理阶段是否错误保持可进入；新案件核对后回到一览，CTA 是否正确变为拟定方案。
- 分享、下载、报告、能力模块和沙盘是否使用当前案件数据，是否可能引用上一个案件的快照。

## 二、后端和 API 审查

- `GET /api/health`、`GET /api/cases`、`GET /api/cases/:id`、`GET /api/cases/:id/report` 和能力模块接口的状态码、响应结构、错误结构是否稳定。
- `POST /api/cases/:id/review`、`propose`、`approve`、`execute`、`close` 是否都严格校验 HTTP 方法、请求体、操作者、案件状态、租户和目标 ID。
- 是否可以直接调用 API 绕过前端，跳过差异核对、材料缺口、负责人确认、执行结果或结案条件。
- `review` 是否只接受当前案件真实存在的冲突 ID，重复 ID、空数组、未知 ID、跨案件 ID 和非法类型是否处理正确。
- 逐项核对请求的服务端串行队列是否覆盖所有需要覆盖的写入；多进程、多容器、服务重启和两个浏览器标签并发时，JSON 文件是否会丢事件或覆盖状态。
- `ensure()` 在 GET 请求中首次初始化并写文件是否符合接口语义；初始化失败、文件损坏、目录不可写时是否会返回误导性的 200 或“无数据”。
- `x-tenant-id`、`x-actor` 是否只是可伪造演示头；生产环境需要补充哪些认证、授权、审计和租户校验。
- `/api/cases` 是否把不应展示的案件全部返回给前端再筛选，是否存在越权或信息泄露。
- 错误是否正确区分 `400`、`404`、`409`、`500`、无效 JSON、非法状态、跨租户和未知案件；是否把异常包装成成功响应。
- `execute` 是否保证所有动作都得到结果后才推进整体状态；`close` 是否保证所有动作已核验且案件状态合法。
- 能力模块的 POST 接口哪些会改变业务状态，哪些只是记录演示事件；响应文案是否诚实。
- 服务端是否存在缓存键、状态快照、错误计数、审计记录或进程内内存状态与实际文件状态不一致的问题。

## 三、数据、证据和业务逻辑审查

- `GoldMaterial → EvidenceItem → ConflictPair → Finding → ActionRecord → AuditEvent` 的字段映射是否完整、稳定、可回源。
- `tenantId`、`scope`、`caseId`、`sourceId`、`sourceVersion`、`locator` 和 `traceId` 是否可能被混用、丢失或伪造。
- 字段归一化、数值比较、金额/数量比较、责任人比较和材料缺口检测是否存在误判。
- 多来源两两比较是否把一个业务问题错误显示成多个问题；产品中的“7 处差异”是否和真实冲突数量一致。
- `Finding.status = accepted` 与 `Conflict.resolution = unresolved` 是否会造成“差异已解决”的语义误解。
- 没有作者、原文、定位、URL、订单号或完整材料的记录是否可能进入报告、行动、回执或结案。
- 报告、关系图、行动拆解、评估脚本和前端是否读取同一份事实，是否存在初始化快照或字段漂移。
- 合成数据、模拟回执、演示租户和真实业务能力的边界是否被文案或接口误导。
- 状态事件的 `from`、`to`、`actor`、`reason`、时间戳和顺序是否可靠；重复请求是否重复推进或重复写动作。

## 四、优先复现场景

请尽量在本地复现，并记录命令、请求体、响应和结果：

1. 首次打开 FX-001 → 查看一览 → 进入核对 → 不完成全部差异时尝试进入处理。
2. 逐项核对 7 个差异 → 检查状态是否按 `new → triaged → confirmed` 推进。
3. 多个核对请求同时发送 → 检查最终 `reviewedConflictIds` 是否完整、无重复、无回退。
4. 核对完成后进入处理 → `propose → approve → execute → close`，检查每个状态和动作结果。
5. `propose` 直接调用、跳过 `review`、带材料缺口调用，检查是否被拒绝。
6. 两个不同 `x-tenant-id` 访问同一案件，检查数据和事件是否隔离。
7. 同一租户两个请求同时修改同一案件，检查是否丢事件、丢动作或覆盖已核对 ID。
8. 发送未知冲突 ID、重复 ID、空数组、数字 ID、空操作者和错误 JSON。
9. 访问未知案件、未知能力模块、错误方法和损坏的 JSON 文件。
10. 使用包含 HTML、引号、换行和恶意属性的案件标题、证据原文和 URL，检查前端输出。
11. 完成一个案件后切换到另一个新案件，再回到一览和处理阶段，检查旧状态是否残留。
12. 服务重启后检查案件状态、已核对差异、事件和回执是否仍然一致。

```markdown

## 2. 问题总表

| ID | 严重级别 | 可信度 | 文件:行号 | 问题 | 影响 |
| -- | ---- | --- | ----- | -- | -- |

严重级别：

- P0：数据泄漏、凭证泄漏、主流程不可用、错误结果被包装成真实事实或可绕过关键审批。
- P1：常见场景下出现关键流程错误、状态污染、数据丢失、租户越权或错误执行。
- P2：明确可复现但影响局部，包括边界输入、并发、缓存、降级和运维诊断。
- P3：低概率问题、文档漂移、可维护性或增强建议。

可信度：

- confirmed：已通过代码和本地复现确认。
- high：代码高度显示存在问题，但需要目标环境确认。
- medium：存在合理风险，需要更多验证。
- low：暂时只是建议或推测。
```
